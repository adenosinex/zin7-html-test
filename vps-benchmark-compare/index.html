① 测量条件与负载背景

  • debi 是满载生产机：测量时段 load 0.10–0.27（单核），CPU 探针 busy 多数时间 4–25%（磁盘轮期间一度读到 52%、load1 0.31），alert 全程 false。在跑：App Hub 平台与 21 个 web 项目、代理全套、AList、Navidrome、Tailscale 等 30+ 服务。它的每个数字都含真实生产噪声，这是「这台机日常能给出的性能」，不是实验室裸机值。
  • shoc 是轻载生产机：load 0.02–0.27，在跑代理与 apirelay 副本，内存可用 1.5G、swap 几乎未动。它的数字更接近裸机上限。
  • 方法：全部测试 nice -n 10 低优先级、单项 ≤25 秒、项间留间隔；fio 测试文件 1G、direct=1、测完即删（两台测前/测后 df 可用量已核对，无残留）。fio 与 sysbench 不是两台的常驻软件，本轮以 Ubuntu 官方 .deb 解包到 /tmp 临时运行，未安装进系统。
  • 异常轮次的处理：只有 debi 内存拷贝的首轮出现首次分配型离群（4.13 / 4.35 秒 vs 稳态 1.6–2.3 秒），已保留在附录原值里并在表中标注，没有删除；其余各项轮间极差都小，稳定性本身就是结论的一部分。

② 结论：两台的硬件画像

  • shoc 是全面更强的机器，且强在最要紧的地方。CPU 单核约快 50%（4215R 对 E5-2670 v2，本质是 2019 年架构对 2013 年架构的代际差）；内存带宽高 40–50%；4K 随机 IO 高约 9.5 倍——127k IOPS 是像样的 NVMe 阵列的形态，13k 则更像 SATA SSD 或被限速的后端。对代理用途：两台都绰绰有余（代理的瓶颈从来是路径不是机器，见 exit node 诊断）；对通用小服务器用途：shoc 的 IO 与 CPU 让它能同时扛代理 + apirelay + 未来杂活，debi 的 4K IO 和 swap 占用决定了它只适合继续做「轻 IO 的应用宿主」，重 IO 任务（批量转码索引、大库重建）放它身上会先撞磁盘再撞内存。
  • debi 唯一反超的是 1M 顺序写（1716 vs 920 MiB/s）：对备份打包、日志、顺序落盘类负载是实打实的安慰；但日常应用的痛点在随机 IO，不在这。
  • steal 两台都是 0，且经旁证复测可信（方法与数据见 ④）：steal 是宿主机「自愿上报」的数字，单看读数不能自证清白——本轮用间隙检测（查周期性限流指纹）、跑分时段稳定性、shoc 满载 5 分钟吞吐曲线三路旁证复核，两台均无「限了但不显示」的痕迹，也无可测的邻居争抢。debi 的弱是「硬件本身老 + 只有 1 核」这种静态的弱，不是被邻居偷走的弱——这个区分重要，因为前者无解（换机才行）、后者可以靠换时段或投诉缓解。旁证的证明力边界（测不出的 HT 争抢 / 降频 / 内存带宽争用）在 ④ 节写明。
  • 容量上 debi 先告急：名义 40G 实给 30G、已用 56%；shoc 30G 只用 14%。debi 的约束顺序是 磁盘 > 内存 > CPU，shoc 三项都还有余量。

④ steal 复测：读数 0 是否可信（2026-11-10 09:46 补测）

为什么要复测：steal 是宿主机通过 kvm_steal_time「自愿上报」的数据，客户机只能信它。宿主机若不开 steal 记账、或用 cgroup CPU quota 限流（被限流的线程已摘出运行队列，往往不计入 steal），steal 可以恒为 0 而限制真实存在。因此「steal=0」本身不能自证清白，必须用不依赖宿主机上报的旁证复核。复测时段 09:46–10:03 CST，与主轮（08:13–08:41）相邻但不同窗。

  • 虚拟化类型（前提核查）：两台 systemd-detect-virt 实测均为 kvm（全虚拟化，非 LXC/OpenVZ 容器）——steal 记账机制存在、上报通道可信度成立；若是容器类（/proc/stat 可被改写），以下读数直接作废。
  • 间隙检测（查 cgroup throttle 指纹）：紧循环 + perf_counter、阈值 2 ms、nice -n 10、每台 3 轮 × 30 s。throttle 的指纹是「每约 100 ms 周期出现一段几十 ms 的停顿」；两台均未见此指纹：
    · shoc（轻载）：>2 ms 间隙共 63 次 / 90 s，间隔中位数 644–1021 ms、无规律；≥10 ms 间隙仅 2 次（最大 12.1 ms）；全部间隙合计占时 0.13–0.32%。
    · debi（生产负载下）：间隙 261 / 431 / 1347 次、合计占时 2.4–11.9%，但 95% 以上落在 2–5 ms 档（真实业务的常规调度抖动），最大一例 15.3 ms，≥25 ms 间隙 0 次、无等间隔周期。量比 shoc 多是它在扛生产的预期形态，不是限流形态——限流看的是「周期性 + 大间隙」，不是计数。
  • 跑分时段稳定性（旁证）：今晨 sysbench 5 轮极差 debi 267–275（±1.5%）、shoc 405–412（±0.9%），轮间极稳；且 debi 有 8 天生产史、多时段读数一致——无「某时段突然掉速」的超售/积分耗尽形态。此旁证证明力有限（同日相邻时段样本，测不出跨日 / 晚高峰的争抢），只作辅证。
  • 长时间满载（只在 shoc 做）：与今晨同一 Python sqrt 内核、每段 3×107 次迭代、连跑 61 段共 300 s（nice -n 10、硬超时 300 s 强停、旁路每 15 s 采 load）。每段耗时 4.69–5.20 s（中位约 4.83 s）：前 10 段均值 4.92 s vs 后 10 段 4.82 s——无阶梯下跌，配额 / burst 积分耗尽形态不存在；旁路 load 从 0.80 平稳升至 1.00 后全程贴 1.00（单核恰好满载），结束后 load 回落至 0.92 并持续下降，无失控。注：满载段单段（约 4.8 s）反而快于今晨轻载三轮（5.57–5.89 s），差异来自解释器热身与测量形态，不作成绩、只看曲线形状。
    debi 侧未做长满载：它是在产主机，资源纪律不允许为验证把它打饱和（见 AGENTS 盒上资源原则）。代偿证据 = 8 天生产史（平台 + 代理全程在跑、从无吞吐塌方记录）+ 多时段 sysbench 稳定 + 本轮间隙检测无指纹；其长满载维度如实记为未测。
  • 综合裁决：两台 steal=0 可信。本轮证据可排除：cgroup quota 周期性限流、配额 / 积分耗尽型限速、本时段内的显著邻居 CPU 争抢。排除不了的（如实列明）：① 超线程兄弟核争抢、宿主机降频、缓存与内存带宽争用——这类「一直在跑、只是变慢」不产生间隙也不产生 steal，只能靠绝对跑分与同型号 CPU 公开成绩的差距间接提示：debi 的 E5-2670 v2 单核 sysbench 273 events/s 与该型号公开量级（约 260–300）相符、shoc 的 4215R 408 与其公开量级（约 400 上下）相符，未见「显著低于同型号」的可疑差距（公开成绩为量级参照、非同场对照，证明力到此为止）；② 晚高峰等其他时段的争抢——全部采样都在上午时段，高峰时段需另测。
